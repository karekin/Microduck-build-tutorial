## 项目与工作路线

### 两条分支

| 路线 | Git 分支 | 做什么 | 默认规模 |
|---|---|---|---|
| 学习 | `codex/microduck-learning` | 体验真实 PPO、保存检查点、导出 ONNX、新策略驱动仿真 | 1个环境，64/32小网络，3项奖励，3轮 |
| 专业 | `codex/microduck-professional` | 在固定官方基础上训练、评估、比较新策略与扩展能力 | GPU链路64环境/5轮；正式基线1024环境/4000轮 |

学习分支只有一个固定零速度的站立任务，Actor 和 Critic 使用相同51维观测。没有课程、推扰、观测噪声、多技能或领域随机化；PPO自身仍会采样探索动作。

专业训练的完整官方源码位于 `professional/upstream/microduck_rl/`，固定版本为 `ceca01706143d729305baa94cbd8ab990979e325`。254个源文件及其SHA256记录在 `professional/upstream.lock.json`。安装和训练使用 `prepare`生成的独立目录，不在固定源码里随手安装依赖或修改实验参数。

### 必须分清的接口

| 运行路线 | Actor输入 | 动作 | 运行程序 | 硬件指南 |
|---|---:|---:|---|---|
| 当前教程 | 已附模型51维；加载器也支持53维phase模型 | 14 | `microduck/` Python控制循环 | Raspberry Pi Zero 2 W教程路线 |
| 当前官方训练与运行栈 | 61维 | 14 | 官方Rust daemon与`robotctl` | 固定官方安装文档针对Radxa Zero 3 |

两条路线都以50Hz控制为基础，但51/53维模型与61维模型不能互换。关节顺序、默认角度、动作比例、单位、IMU坐标系、命令槽和归一化都必须匹配。不能通过补零、截断权重或修改输入形状完成所谓迁移。

### 训练与部署各用什么

```text
电脑：修改配置、CPU预检、查看仿真
  → GPU机器：并行物理仿真与PPO更新
  → 检查点 .pt：网络、优化器、归一化和训练状态
  → ONNX .onnx：供运行程序计算动作
  → 部署仿真：使用实际控制程序核对策略行为
  → 合格硬件：分阶段实机验证
```

PPO是学习方法，MuJoCo是物理仿真器，神经网络是学到的控制器，ONNX是模型交换格式，ONNX Runtime是执行推理的软件。云端训练不要求把实机接到云端；机器人的实时控制通常在板端本地运行。

## 专业模型能力与突破方向

截至2026年10月10日，本项目实际训练并回收的专业模型是`model_5.pt`及其`policy.onnx`：64环境、5轮PPO、7680条样本。它能完成CUDA训练和策略推理，61维输入生成14个关节动作；48步物理评价有1次复位、最大倾角约68.54°，尚未得到稳定行走或实机能力。

以下是官方固定代码已提供的训练任务，不等于这份五轮模型已经掌握全部技能：

| 能力方向 | 官方任务族 | 本项目当前状态 |
|---|---|---|
| 平地和粗糙地面行走 | Velocity Flat/Rough，速度及头部命令 | 仅平地任务做过短GPU链路验证 |
| 行走与跌倒恢复 | VelStand Flat/Rough | 有任务，未完成正式训练评价 |
| 从地面起身 | StandUp Flat/Rough | 有任务，未训练验收 |
| 坐下与站起 | SitStand Flat/Rough | 有任务，未训练验收 |
| 低头触地并返回站立 | GroundPick Flat/Rough | 有任务；不等于已实现视觉识别和可靠物体抓取 |
| 踢球 | BallKick Flat | 有任务，需把踢完站稳率一起验收 |
| 前滚翻与落地 | Roulade Flat | 有任务，接触/落地需独立评价 |
| 轮滑、swizzle、滑行蹲姿、坡面滑行及旋转 | Rollers等任务 | 有任务，需要相应轮式机构模型与硬件 |
| 齿轮间隙鲁棒性 | 多个Backlash变体 | 官方机制已提供，需按实际舵机校准并做A/B |

专业库使用共同61维接口，包含48维本体状态和13维速度/头部/躯干命令槽。统一输入便于策略切换，但每个技能的命令语义与碰撞模型不同，不能靠替换文件让同一模型自动拥有所有能力。

进一步突破按产品目标推进：

1. **可靠运动基线。** 先正式训练站立、低速从静止起步、停止、转向和后退。冻结评价场景，至少多seed复验，并报告跌倒、速度误差和横漂。
2. **仿真到实机的一致性。** 校准已有BAM电压/摩擦/延迟机制、齿轮间隙、机械零位、IMU方向和实际报告延迟；验证随机化真实生效且reset不累加。
3. **恢复与动作衔接。** 验证VelStand，再逐项增加坐站、触地、踢球；动作结束回到站立并切回行走也属于成功条件。
4. **适应未知条件。** 在固定PPO基线上比较短历史观测、循环网络、教师学生/RMA；同步设计部署缓存、隐状态重置和推理预算。框架或脚本存在不等于模型已经具备在线适应。
5. **自然性与样本效率。** 有适配的参考动作后再实验AMP；SAC/TD3应按同任务、同奖励、同算力及独立评价对照，不能仅凭社区视频宣布优于PPO。
6. **任务层产品能力。** 视觉感知、目标选择、路径规划、任务编排和安全控制是另外的模块。当前本体步态模型不是能理解语言、视觉导航、抓取任意物体的通用机器人模型。

首要突破是从“链路跑通”进入“可重复、可测量的稳定行为”。不要同时更换算法、物理引擎、执行器和奖励，否则无法定位能力提升或退化的来源。

## 软件与账户准备

### 电脑准备

本手册的主要命令使用macOS或Linux终端。Windows同学可在Linux开发机或WSL2中先做无界面检查；Windows原生窗口、WSL图形与GPU驱动链未在本项目验收，不能把Mac结果直接当成Windows结果。

准备Git、Python3.12、uv和网络连接。建议保留至少10GB可用磁盘；若同时保留多套环境、GPU模型和视频，预留更多。专业训练使用Linux NVIDIA CUDA；Mac学习流程使用CPU，苹果GPU的可用性不代表当前MuJoCo Warp路径能自动使用MPS。

macOS和Linux均可使用uv官方安装器：

```bash
curl -LsSf https://astral.sh/uv/0.11.30/install.sh | sh
```

重开终端或把安装器显示的目录加入PATH，再确认：

```bash
git --version
uv --version
uv python install 3.12
```

`0.11.30`与已跑通的云端安装器保持一致；不要为解决一个错误同时升级Python、Torch、MuJoCo和BAM。安装方法见[uv官方文档](https://docs.astral.sh/uv/getting-started/installation/)。本地已装uv的成员可继续使用现有版本，但要记录版本并保持`uv.lock`不变。

### 环境分开安装

| 环境 | 安装目录 | 用途 |
|---|---|---|
| 学习训练环境 | 学习分支的`mjlab_microduck/.venv` | 小网络PPO与学习查看器 |
| 教程运行环境 | 所在分支的`microduck/.venv` | 51维模型推理、MuJoCo仿真、教程板端程序 |
| 专业官方环境 | `professional/runs/official/.venv` | 61维官方训练、导出、CPU预检与部署仿真 |

每套环境有自己的锁文件。使用绝对解释器路径或指定工作目录，不依赖某个恰巧已经激活的环境。`uv sync --frozen`按已有锁文件安装，不重新解析并升级版本；联网下载和模型资源仍是首次安装的前置条件。

### 云账户

每位成员使用本人或团队批准的Hugging Face账户，确认计算额度、任务权限及本轮预算。网页登录与本地CLI登录是两件事；只在网页登录不会自动给本地SDK提供凭据。

团队管理员负责预算与账户授权，实验负责人负责源码版本、任务监控和停止，算法同学负责评价，硬件负责人负责板型、机械零位和实机放行。团队可合并角色，但每轮实验必须知道由谁回收资源和核对结果。

## 取得项目与建立工作目录

### 当前交付包

2026年10月10日，两条新分支已在本机提交，尚未发布到远端。当前可用`Microduck-team.bundle`分发已提交源码和手册；此包不依赖共享某位成员的虚拟环境。团队维护者以后可以自行发布远端分支，再使用普通Git克隆流程。

将交付包下载到自己的电脑。在希望存放项目的位置打开终端：

```bash
mkdir -p Microduck-workspace
cd Microduck-workspace

# 将/path/to替换为交付包的实际位置。
git clone --branch codex/microduck-professional \
  /path/to/Microduck-team.bundle Microduck-professional

git -C Microduck-professional worktree add --track \
  -b codex/microduck-learning ../Microduck-learning \
  origin/codex/microduck-learning

export MICRODUCK_PRO="$PWD/Microduck-professional"
export MICRODUCK_LEARN="$PWD/Microduck-learning"
```

这里的`origin`指向bundle文件，不是GitHub。检查两个目录分别在哪条分支：

```bash
git -C "$MICRODUCK_PRO" branch --show-current
git -C "$MICRODUCK_LEARN" branch --show-current
```

预期分别为`codex/microduck-professional`和`codex/microduck-learning`。后续命令默认在同一终端执行；新开终端时重新设置两个路径变量。已有项目的成员直接把变量设置为自己的目录即可，不要在有未提交改动的目录强行切分支。

命令中的`YOUR_HF_NAMESPACE`、`YOUR_JOB_ID`、`RUN_DIRECTORY_NAME`、`USER@ROBOT_HOST`和`/path/to`均是占位符，执行前先替换成实际值。带`--submit`、`--execute`或连接设备的命令会产生真实操作，不属于纯说明预览。

### 分支发布后的替代方式

仅在维护者确认远端已有两条分支后，才使用下列克隆方式：

```bash
git clone --branch codex/microduck-professional \
  https://github.com/karekin/Microduck-build-tutorial.git Microduck-professional
```

再按前面的`git worktree add`建立学习目录。无法找到远端分支时先使用bundle，不能把`main`当成含有最新训练入口的专业分支。

## 学习分支快速体验

### 安装独立环境

```bash
cd "$MICRODUCK_LEARN/mjlab_microduck"
uv sync --frozen --python 3.12
cd "$MICRODUCK_LEARN"
```

### 运行完整闭环

```bash
./learn.sh
```

入口依次运行CPU物理环境、真实PPO更新、保存并重载新`.pt`、导出含归一化的ONNX、比较真实观测上的输出，再用新ONNX驱动物理仿真48步。最后应出现`status: PASS`和产物目录。

本机已有缓存时此前约12秒；本轮独立环境安装后的第一次完整运行约68秒。首次导入与物理内核编译可能更慢，不要按固定秒数判定失败。

### 查看刚训练的策略

```bash
./learn.sh --view
```

打开终端打印的本地地址，并保留末尾斜杠，例如`http://127.0.0.1:8080/`。使用查看器播放控件；终端Ctrl-C结束。浏览器需要WebGL；若提示WebGL不可用，先检查浏览器/图形环境，再使用无界面流程或原生MuJoCo检查。模型可能跌倒并自动复位，这是几轮训练的正常可能结果，不能因此认为训练程序是假运行，也不能把显示出机器人当成站立成功。

需要更多教学轮数时：

```bash
./learn.sh --iterations 10 --rollout-steps 100
```

该命令仍是学习任务，不会切换到专业技能或启动云GPU。

### 查看产物

读取`learning_artifacts/latest.json`，再打开其中的`report`路径。每轮产物在独立时间目录中：

| 文件 | 用途 |
|---|---|
| `LEARNING_ONLY_NOT_FOR_HARDWARE.pt` | 保存训练与归一化状态 |
| `LEARNING_ONLY_NOT_FOR_HARDWARE.onnx` | 新策略推理图 |
| `result.json` | 参数变化、训练步数、导出误差、物理步数、复位与耗时 |
| `failure.txt` | 失败的原始错误，若本轮失败 |

学习PASS必须包含Actor MLP参数实际变化、ONNX检查与输出比较通过、物理状态有限且改变，以及旧策略文件哈希不变。学习产物禁止直接安装到实机。

## 本地仿真环境

### 教程51维运行程序

专业与学习分支均保留`microduck/`。在希望使用的分支目录安装：

```bash
cd "$MICRODUCK_PRO/microduck"
uv sync --frozen --group sim --python 3.12
.venv/bin/python -m unittest discover -s tests -v
```

本轮独立安装后18项运行回归通过。先跑无界面版本：

```bash
.venv/bin/python src/sim/sim_main.py \
  --headless --walk --ticks 100 --log logs/first-sim.jsonl
```

此命令仅在电脑上运行，100个50Hz控制周期对应2秒仿真时间。`--walk`开启已有策略；默认速度命令为零。查看最后的summary，核对`ticks`、`requested_ticks_completed`、最低高度、低高度周期和策略实际激活周期，不能只看进程退出码。

较长检查可用：

```bash
make sim-headless
```

它运行500周期，并写`logs/standing.jsonl`。文件名不表示站立或通用行走已经验收。

### 打开MuJoCo窗口

```bash
make sim
```

Mac由Makefile选择`mjpython`，Linux选择`python`。当前窗口入口默认不开启行走，需按`v`启用已有策略；按`q`或终端Ctrl-C退出。第一次只检查机器人显示、复位、零速度策略和日志，再进行速度输入试验。

若要显式指定Mac解释器：

```bash
PYTHONPATH=src .venv/bin/mjpython src/sim/sim_main.py --hz 50
```

`sim_main.py --help`列出速度、延迟、增益和模型初始高度参数。速度参数为归一化输入，而非直接的m/s；输入经过`scale_velocity`映射。当前分发分支没有原教程工作目录中尚未提交的额外launcher和heading-assist，不能把这些功能写进验收记录。

### 仿真与实机的区别

仿真不会打开真实串口；启动记录含`hardware_verified=false`。某组零延迟、特定增益下的仿真结果不能代替实际传感延迟、电压、机械零位和地面摩擦测试。模拟器与策略、执行器模型也需要版本对应。

## 专业分支安装与预检

```bash
cd "$MICRODUCK_PRO"
uv run --no-project --python 3.12 python professional/run.py verify
uv run --no-project --python 3.12 python professional/run.py prepare
```

`verify`应显示254个文件校验通过。`prepare`输出`professional/runs/official`，该目录有独立Git根，HEAD为固定官方版本。新克隆没有原官方Git对象时，会从官方仓库获取这个确切版本；仍需要访问GitHub。

安装官方独立环境：

```bash
cd "$MICRODUCK_PRO/professional/runs/official"
UV_HTTP_TIMEOUT=600 uv sync --frozen --python 3.12
cd "$MICRODUCK_PRO"
uv run --no-project --python 3.12 python professional/run.py cpu-check
```

预期Actor`[1,61]`、Critic`[1,76]`、14个动作，3次实际CPU物理步进，有限观测/奖励。此项不进行PPO训练。每次报告和日志放在新的`professional/runs/cpu-check-*`目录。

运行本项目工作流回归：

```bash
professional/runs/official/.venv/bin/python \
  -m unittest discover -s professional/tests -v
```

当前共12项，涵盖来源、接口、预算、目录准备和GPU证据。它们不是完整官方测试集，也不证明长期步态稳定。

`prepare`拒绝覆盖已有不同HEAD或未提交修改的官方目录。出现此错误先保存实验改动并核对目录用途，不要删除结果或强行重置到某个版本。

## Hugging Face 在线 GPU 链路

### 登录与预算

先在[账单页面](https://huggingface.co/settings/billing)确认额度，区分预充值金额与实际算力消耗。本轮实例为L4 24GB，官方价格约$0.80/小时，按分钟计费；价格和库存以提交时的API及页面为准。[官方计费](https://huggingface.co/docs/hub/en/jobs-pricing)

Jobs可由有正数计算额度的用户或组织使用，首次试跑不要求额外订阅PRO。充值与每轮算力预算分别由团队确认；默认不启用自动充值。

使用支持浏览器授权的CLI登录：

```bash
uv tool run --from huggingface_hub==1.33.0 hf auth login
```

按终端提示在浏览器输入设备码并核对权限。团队成员自行完成账户授权；不要把密码、卡号或token写进代码、聊天、报告或分发包。若使用细粒度token，需要满足本轮Jobs和私有源/结果仓库操作权限。本地`hf auth login`成功后，项目SDK使用缓存登录。

### 先生成准备包

```bash
cd "$MICRODUCK_PRO"
professional/runs/official/.venv/bin/python professional/hf_hour.py
```

该命令只生成源码包与`receipt.json`，不会租GPU。它打包固定官方源码和`gpu_pipeline.py`，不复制整套本机工作目录。终端显示的receipt属于此次准备包；未提交的receipt没有job_id，不可拿它查询任务。

### 实际提交

确认本轮预算后，仅提交一次：

```bash
professional/runs/official/.venv/bin/python professional/hf_hour.py --submit
```

脚本固定L4、3600秒超时，提交前按实时分钟单价计算小时价格；超过$0.80拒绝提交。源包和结果仓库为私有，凭据通过HF任务秘密参数传入。它使用官方锁文件安装Python3.12依赖，然后实际完成：

1. CUDA身份核验，GPU不可用即失败，不回退CPU。
2. 64环境、5轮、seed42，共7680条PPO样本，检查MLP参数确实更新。
3. 完整检查点保存和重载。
4. 61→14 ONNX导出、归一化与数值比较。
5. 独立play环境48步由新ONNX驱动物理，检查有限状态、变化、倾角和复位。
6. 上传报告、模型、日志和配置，退出任务。

刚提交时通常先处于SCHEDULING拉取镜像，再RUNNING安装依赖、编译物理内核。冷启动耗时不等于PPO耗时。查看状态、job_url和模型仓库地址，不要因为暂时没有训练日志再次点击提交。

网络错误发生在提交期间时，先查看原receipt和账户Jobs，按run_id标签确认是否已经创建。脚本不自动重试未知的付费提交；重复运行`--submit`会产生另一次申请，不是查询按钮。

### 查询和回收

把下面路径替换为**实际提交**时打印的receipt：

professional/runs/official/.venv/bin/python professional/hf_hour.py \
  --receipt "$MICRODUCK_RECEIPT"

professional/runs/official/.venv/bin/python professional/hf_hour.py \

模型位于receipt同级的`downloaded/runs/<时间>/`，包括`model_5.pt`、`policy.onnx`、`result.json`、`manifest.json`、`pipeline.log`和`params/`。

## Linux GPU 与正式训练

一小时入口用于首次链路验证。专业能力训练通常需要更大批量、更长课程与独立评估，不能把默认5轮模型提升为产品默认策略。

### 自己租Linux GPU实例

AutoDL、RunPod Pods或其他支持Linux NVIDIA CUDA的平台均可承载训练。起点可选24GB显存的单卡；先测64/512/1024环境的显存和吞吐，再决定4096环境。不要为当前小网络直接预订多张A100或H100。

实例上安装Git、uv、Python3.12，获取专业分支，并执行前面的`verify`、`prepare`和官方`uv sync --frozen`。GPU检查：

```bash
nvidia-smi
cd "$MICRODUCK_PRO"
professional/runs/official/.venv/bin/python -c \
  "import torch; print(torch.__version__, torch.version.cuda, torch.cuda.is_available())"
```

`torch.cuda.is_available()`必须为True。只看到nvidia-smi成功不代表Python安装了正确CUDA版Torch。

### 先做小规模检查

```bash
uv run --no-project --python 3.12 python professional/run.py train
uv run --no-project --python 3.12 python professional/run.py train --execute
```

第一条只显示命令；第二条在已安装的官方目录中启动64环境/5轮本地CUDA训练。需要完整链路验证时，使用`hf_hour.py`，或在独立官方目录中复制本项目`gpu_pipeline.py`后按其`--help`运行；默认CUDA，不连接硬件。

### 正式基线

```bash
# 在专业分支根目录，先检查命令，确认预算和资源再加--execute。
uv run --no-project --python 3.12 python professional/run.py train \
  --profile baseline --task walk --num-envs 1024 --seed 42
```

该预设为4000轮；完成一轮seed42筛选后，再做43/44复验。观察主任务指标、每项奖励贡献、episode长度、损失/探索程度、NaN、显存和采样吞吐。奖励总和提高可能只是正则项改善，仍需看跌倒率、速度误差和视频。

托管HF正式训练的命令生成与实际执行：

```bash
uv run --no-project --python 3.12 python professional/run.py train \
  --backend hf --namespace "YOUR_HF_NAMESPACE" --profile baseline \
  --task walk --num-envs 1024 --seed 42 --timeout-minutes 60
```

加`--execute`才提交。此入口使用官方HF训练/上传/导出流程，不是前面带专用下载验证的`hf_hour.py`。按终端打印的模型仓库地址回收检查点；不能拿它的job_id冒充`hf_hour.py`的receipt。到超时但未收敛时，本轮只是中断或失败，保留已上传检查点，续训另有预算。

任务别名为`walk`、`walk-backlash`、`recovery`、`standup`、`sitstand`、`kick`。先平地行走基线，再齿轮间隙、电压/摩擦/延迟和恢复；动作技能逐个引入。

### 恢复训练

在独立官方目录，使用已知任务对应的检查点和环境：

```bash
cd "$MICRODUCK_PRO/professional/runs/official"
uv run --frozen train Mjlab-Velocity-Flat-MicroDuck \
  --env.scene.num-envs 1024 \
  --agent.resume True \
  --agent.load-run "RUN_DIRECTORY_NAME" \
  --agent.load-checkpoint model_1000.pt \

```

路径选择以运行日志和实际文件为准；`max-iterations`表示该次追加迭代。恢复同一任务要保留完整训练状态。跨任务warm start涉及归一化、课程计数和任务兼容性，不能直接当成普通resume；先读固定源码AGENTS与任务说明。

## 模型导出与部署仿真

### `.pt`与`.onnx`

`.pt`是训练检查点，供继续训练或导出；`.onnx`是运行程序读取的推理图。ONNX并非机器人专用，也不包含可直接替代全部训练状态的保证。更换文件后，运行程序还要把传感器数据按正确语义构造成输入。

加载团队生成、来源与哈希可核对的检查点。旧教程附带`velocity.pt`为63维观测/18动作，不能用于当前14关节任务；不要截断或改形状。

### 专业61维导出

```bash
cd "$MICRODUCK_PRO/professional/runs/official"
export MICRODUCK_CHECKPOINT="/absolute/path/to/model_1000.pt"

uv run --frozen python scripts/export.py Mjlab-Velocity-Flat-MicroDuck \
  --checkpoint-file "$MICRODUCK_CHECKPOINT" --device cpu \
  --num-envs 1 --onnx-file output.onnx
```

使用对应任务导出。官方入口将观测归一化写进图中；不要手工转换后遗漏归一化。检查61维输入、14动作、关节名称顺序、默认姿态、action_scale、控制频率与模型元数据。

### 官方CPU部署仿真

Linux桌面：

```bash
uv run --frozen python scripts/infer_policy.py \
  --walking /absolute/path/to/policy.onnx --new-cmd-obs
```

Mac的MuJoCo原生窗口需要mjpython：

```bash
uv run --frozen mjpython scripts/infer_policy.py \
  --walking /absolute/path/to/policy.onnx --new-cmd-obs
```

此程序用于CPU部署仿真，使用实际BAM执行器模型；并非实机控制。`--new-cmd-obs`对应61维统一命令槽；不同技能的phase/posture命令语义需按官方任务处理。`--save-csv /path/eval.csv`可保存观测和动作；`--record`保存的是观测记录，不应当作视频参数。

Mac若窗口失败，先保留错误，再用学习查看器、无界面检查或Linux桌面排查。当前原生官方查看器的跨平台画面/交互尚未纳入本机验收。

## 教程硬件部署

以下为51/53维Python教程路线。会连接设备的命令只在硬件负责人完成前置检查后执行。本项目已验证软件与模拟流程，尚未把任何当前教学/五轮GPU模型验收为实机步态。

### 设备与机械前置检查

确认板型/系统镜像、UART/I2C、供电与共地、舵机型号和总线、14个ID、关节转向、机械零位、IMU安装方向/报告率与延迟。先单关节，再悬空，再支撑站立，最后低速平地；每一步保留配置与结果。

当前ID映射来自`microduck/src/constants.py`：

| 部位 | 关节与ID |
|---|---|
| 右腿 | yaw5、roll4、pitch3、knee2、ankle1 |
| 左腿 | yaw10、roll9、pitch8、knee7、ankle6 |
| 头颈 | neck_pitch12、head_pitch11、head_yaw13、head_roll14 |

当前代码包含用户机构的膝关节±45°零位偏移；新机器人不能把它当成通用机械零位。常量里的增益、电流保护阈值和IMU四元数也需与实际机构核对，不能仅因仿真通过而照搬。

镜像来源、校验值和首次账号按原教程的对应Release与README确认。刷写会替换目标SD卡内容，由硬件负责人确认盘符与镜像版本；本手册不提供对未知磁盘执行的克隆/擦除命令。

### 登录与只读检查

```bash
ssh "USER@ROBOT_HOST"
```

设备上先确认OS版本、Python/uv、串口设备与I2C配置。不要把未知设备主机密钥错误直接忽略。RobotController会尝试OpenRB、ttyACM0和板载串口，找不到仍可能退回ttyAMA0；必须确认实际路径和权限。

### 同步并安装

在开发电脑的教程`microduck/`目录：

```bash
cd "$MICRODUCK_PRO/microduck"
export MICRODUCK_HOST="USER@ROBOT_HOST"
make setup HOST="$MICRODUCK_HOST"
```

该命令同步源码，并在设备`~/microduck`执行冻结依赖安装；设备必须先有uv和网络。同步排除仿真、文档、日志等目录，不等于镜像发布或完整远端一致性验收。

传感器和电压检查入口：

```bash
make imu HOST="$MICRODUCK_HOST"
make voltage HOST="$MICRODUCK_HOST" ID=2
make imu-check HOST="$MICRODUCK_HOST"
```

这些make入口先同步软件，然后连接传感器或总线。电压脚本会设置舵机`status_return_level=1`，串口固定为`/dev/ttyAMA0`，并非完全只读，也不采用RobotController的自动端口枚举；运行前核对对应板端UART、供电和ID。连续采样按Ctrl-C结束。`make run`没有串口参数，不能用`SERIAL_PORT=...`假装修改主控制入口；该变量只被特定方向检查命令使用。

### 启动与停止

机器人有可靠支撑、机械检查通过且模型已完成对应实机放行后：

```bash
make run HOST="$MICRODUCK_HOST"
```

启动会开启舵机扭矩并回到neutral姿态。先支撑再启动，不把它当作第一次枚举硬件的命令；同一总线只运行一个控制进程。

停止：

```bash
make stop HOST="$MICRODUCK_HOST"
```

先支撑机器人。正常Scheduler清理会关闭扭矩，机器人可能失去支撑；`stop.py`发SIGINT，超时再SIGTERM。强制终止、启动失败或通信故障不能保证正常清理完成，必须观察进程和实际扭矩状态并使用设备的物理停止措施。

安全关机：

```bash
make shutdown HOST="$MICRODUCK_HOST"
```

按设备关机过程完成后再断电。手柄daemon连接时可能关闭Wi-Fi；SSH不通时先检查手柄/网络状态，不能假定停止命令已经送达。

### 模型更新与回退

只使用已验收、接口匹配的模型。停止控制，备份当前51维策略并保存SHA256；把候选放到`microduck/src/agents/walk.onnx`，同步后重新启动才会加载。运行控制器前再次核对shape、joint_names、default_joint_pos和action_scale。

出现退化时停止控制并恢复匹配的旧模型，再同步并重新验证。`make sync`不带`--delete`，不能把一次同步当成完整系统回滚。教程没有官方`robotctl`的签名更新/daemon回滚系统。

## 故障排查

| 现象 | 先检查什么 | 处理方向 |
|---|---|---|
| 找不到分支 | 远端是否发布；bundle是否包含两个refs | 使用已交付bundle，不把main替代专业分支 |
| 找不到Python/uv | PATH、版本、工作目录 | 用uv安装Python3.12，重开终端；不混用环境 |
| 模块找不到 | 当前目录、解释器和对应uv.lock | 在正确子目录冻结安装，保留安装日志 |
| 首次运行很慢 | 是否下载依赖或首次编译内核 | 等待并看CPU/日志；不重复启动付费任务 |
| 本地查看器404 | 系统Python/代理是否改写无斜杠URL | 使用末尾`/`和项目Python；给127.0.0.1设置代理例外 |
| 查看器Connected但无3D画面 | WebGL与浏览器图形环境 | 页面连接不代表3D通过；换受支持环境或用无界面/原生MuJoCo |
| `CUDA unavailable` | Torch版本、CUDA轮子、驱动、GPU可见性 | 在Linux GPU检查；不要在Mac冒充CUDA测试 |
| HF未登录/401 | 网页和CLI是否分别完成登录 | 本人完成CLI登录；不把token发到聊天 |
| HF403 | Jobs/仓库权限、命名空间是否正确 | 按账户管理员确认权限，不把它当成余额不足 |
| HF402或额度错误 | 可用额度与账户命名空间 | 核对账单；充值金额需单独确认 |
| 任务长时间SCHEDULING | 镜像、挂载和资源排队 | 查看原job，不盲目再提交；无进展则按预算停止 |
| 只有.pt没有ONNX | 导出步骤是否失败/超时 | 保留检查点，按匹配任务单独导出并核对元数据 |
| `prepare`拒绝目录 | HEAD或未提交改动与固定版本不同 | 保存改动，建立独立实验目录，不覆盖原始结果 |
| 51/61或关节顺序错误 | 模型所属路线、task、元数据 | 找到匹配模型与程序；不能补零或截断 |
| Mac窗口失败 | 是否用了mjpython、libpython/原生库错误 | 无界面先验证，再按当前环境诊断 |
| 日志文件叫standing却跌倒 | summary、倾角、复位、命令和延迟 | 文件名不是验收；保存失败、做单因素对照 |
| 串口无回复 | 端口、权限、1Mbps、供电、14个ID | 先枚举与硬件校准，不直接运行完整行走 |
| SSH不通 | 账号/IP、Wi-Fi、手柄daemon | 确认网络与设备状态，不能当作停止已生效 |
| 官方duck-sim失败 | 短socket路径、Rust、duck-body和ORT库 | 核对固定官方指南；减少相机和机器人数量 |
| 候选模型退化 | 模型/配置/seed/评价版本是否相同 | 停止发布，恢复合格基线，保留候选证据 |

遇错先保存命令、工作目录、分支/commit、软件版本、原始日志和对应result，不仅截一行报错。不要用删除失败目录、重置整个仓库、取消锁文件或一次升级所有依赖来掩盖原因。
